# Repository refinement

Add `refine` to an owner-authored issue. `lighthouse-sdlc-router.yml` authorizes the event and calls the gh-aw refinement worker. An owner reply to a pending `needs-info` question resumes that stage. SoFa observes GitHub evidence independently; its service and database are not needed.

The issue and explicit owner answers are the product-intent record. ProductShape and ArcShape are not installed authorities here. Refinement defines scope and acceptance criteria; `ready` never grants implementation or merge authority. Add `propose` to explicitly request a proposal from the ready issue.

Open the Actions run linked from the result comment. Preparation verifies the request and reserves the issue with `agent-working`. For live progress, open `refine / agent`, `propose / agent` or `implement / agent`, `integrate / agent` or `review / agent` → `OpenCode progress and result`. It shows public agent updates, one-line tool activity, elapsed-time notices during quiet intervals and the validated result. The other jobs prepare, authorize, publish and close the execution; they are not separate agent assignments. The agent job summary contains the refinement result. Download `opencode-events` for redacted structured diagnostics, gh-aw artifacts for session and usage evidence, and the Lighthouse result artifact for the envelope and runtime receipt. Publication validates the result and rereads source and owner answers before setting `ready` or `needs-info` and releasing the reservation. Artifacts follow GitHub retention and are not a permanent archive.

Bastion provides a dedicated runner container labelled `lighthouse-workflow`. Each engine invocation uses a temporary container with packaged skills; refinement and proposal source is read-only, while implementation receives a disposable writable copy. Runtime authentication remains operator-owned. The Docker subscription profile has outbound networking and does not provide AWF egress filtering or credential proxying. The workflow pins its Lighthouse implementation independently of the foundation version. Update it with the SDLC package's `install-workflows.mjs`, then commit the reviewed sources and compiled lock together. `LIGHTHOUSE_AUTOMATION_ENABLED` is the repository execution switch.

To take over active work, add `human-working` and cancel or wait for the Actions run. That label reserves work; `needs-info` means waiting for an answer. Labels cannot lock out arbitrary editors. A changed issue, answer or source prevents publication. Inspect failed runs before retrying or clearing a stale `agent-working` reservation. After three unresolved answer rounds, add `refine` explicitly to request another attempt.

This repository enables refinement, proposal delivery and bounded implementation. `propose` authenticates the successful refinement and requires the same source revision and owner intent; run `refine` again after source or intent changes. Preparation gets OpenSpec 1.15.0 templates from the provider. The engine returns proposal, design, specification and task files, and the publisher runs OpenSpec strict validation before creating a PR under `openspec/changes/issue-<number>-proposal/`. No provider installation is needed in the product or engine image. The immutable workflow pin selects this capability independently of the installed foundation package.

For issue 18, the [inspected keynote reference](../research/standalone-keynote-reference.md) supplies source and screenshot observations for proposal work in the sandbox. Use that research as reference context; final visual acceptance still requires our own rendered preview.

Review the linked proposal PR when the issue shows `waiting-review`. It contains the proposed design and unchecked implementation tasks. A blocked proposal uses the same attention label and explains the missing decision without creating a PR. Comments do not automatically continue proposal work. Existing proposal directories or open proposal PRs stop a new attempt; the worker does not overwrite them. If publication fails after branch creation, inspect that branch before retrying. Use `--with-propose` when regenerating these workflows.

Actions is allowed to create PRs, with read-only default tokens and a reasoned `actions.workflow` exception in the GitHub profile. GitHub groups that setting with the ability to approve PRs; the proposal and implementation publishers never approve or merge. PRs created with the workflow token generate checks that require maintainer approval: inspect the changes, then select **Approve workflows to run** in the PR. This authorizes CI execution; accepting the proposal and authorizing implementation remain separate decisions. See [GitHub token-triggered runs](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs). Catalogue verification and Lighthouse guardrails remain separate CI checks. Implementation is opt-in through `--with-implement`; completion is opt-in through `--with-completion`, with an explicit owner dispatch for each stage.

## Request implementation

After accepting and merging the OpenSpec proposal, add `implement` to the issue. The owner request and `.lighthouse/implement.json` authorize the proposal number, scope, writable paths and check commands. The worker verifies the proposal was merged by the owner and its artifacts remain unchanged. It stops if another implementation PR is open. The issue label alone cannot authorize arbitrary writes.

OpenCode edits and tests in a disposable container with a 30-minute execution limit. The host reconstructs the candidate and reruns the configured commands in a fresh container without provider or GitHub credentials. The publisher rechecks source and owner answers before creating a new PR. `implementation-evidence` contains host check logs and agent screenshots, reports and retrospective; `lighthouse-result` contains the candidate and receipts. These are retained Actions artifacts, not a permanent archive. Failed checks or required human acceptance produce a draft PR and `waiting-review`. They never mark the issue done or authorize merge.

Issue 18 uses proposal #33. Review both complete rendered talks and their content maps before accepting the migration. The agent cannot change workflows or Lighthouse policy; the maintainer updates the catalogue CI separately once the candidate build and tests exist. Approve bot-created PR workflows in GitHub before relying on their results. Additional work on an open implementation PR requires an explicit maintenance step; this worker never overwrites its branch.

## Integrate and review

Use **Actions → Lighthouse SDLC router → Run workflow** on `main`. Select `integrate`, enter the issue and PR numbers, and paste the full accepted PR head SHA. Leave `merge` false to check and prepare; set it true to authorize merging that exact revision. Changed code, intent, policy, reviews or base stops publication until a fresh owner request. GitHub still enforces required checks and protection. Labels and ordinary comments do not authorize these stages.

The publisher records the actual merged commit and explicitly dispatches `verify-catalog.yml`, since a merge made with the Actions token does not trigger ordinary push CI. When verification finishes, request `review` with the same issue, PR and accepted head, leaving `merge` false. Review can also inspect an already merged delivery; it does not merge it again.

OpenCode reports its assessment in the agent job. The trusted publisher links the issue and PR to reports pinned to a commit on the protected `process/retrospectives` branch. Review retains findings, affected-instruction drift and an evidence-backed retrospective; it does not automatically create issues or change policy. A passed review closes the work item; unresolved findings leave it awaiting review. Earlier screenshots keep their existing locations, including the permanent issue 18 bundle.
